## Owner-confirmed final Auth UX — policy, not implementation

- **Sign Up:** Email → six-digit OTP → Create Password → required Cloud Profile → Local Fitness Onboarding → Home. Initial password enrollment follows successful server verification only. Reuse the same safely surviving provisional Supabase UUID; never enroll a password-complete account through Sign Up. The approved Account Setup and fitness screen order remains in the [lifecycle contract](../../../docs/27-OTP-FIRST-AUTH-LIFECYCLE.md).
- **Sign In:** Email → Continue → Password → `signInWithPassword`. Keep Email visible when Password appears. Normal Sign In sends no OTP and changes no password. A valid persisted same-user session skips unnecessary Sign In; trusted server eligibility and same-UUID encrypted local safety still determine the destination.
- **Forgot Password from Login:** Login Password screen → Forgot Password → Confirm Email → six-digit Recovery OTP → Create New Password → Continue → Login screen with Email prefilled. Report success only after the trusted server confirms the password update. Do not enter Home from recovery. Clear recovery-only session state, code, new-password input and other sensitive temporary values; require explicit `signInWithPassword` using the new password. Preserve generic public responses.
- **OTP presentation when separately implemented:** six-digit accessible input, numeric keyboard, paste support, invalid-code error that preserves navigation, server-derived resend countdown and Send Again. The server enforces expiry, resend and failed-attempt limits; the UI timer is informational. Preserve existing Expo preview text, visual design, layout, focus, keyboard behavior and accessibility. Task 06C does not modify UI.

## Signup versus recovery authorization boundary

Native Email OTP verification can issue an Auth session; the reviewed GoTrue version classifies ordinary OTP and explicit Recovery as recovery-capable for password updates. Consequently, two different screens or OTP email templates do **not** prove two different Auth permissions. A recovery-only session, if native recovery is used, must not silently become a normal Home session or bypass protected cloud gates. `AUTH-17` remains **FAIL** until direct calls prove otherwise.

The preferred **controlled alternative, not implemented**, uses server-owned, one-time, purpose-bound `signup_initial_password` and `recovery_password_reset` challenges. The trusted server independently checks the lifecycle and exact UUID before either privileged Auth operation: create or reuse a provisional UUID for first password enrollment, or update only an existing password-complete UUID after explicit recovery verification. Recovery grants no client Auth session; after confirmed Admin update the client clears transient state and returns to password Sign In. A retry or partial failure must not double-enroll, change another UUID or display false success. The Auth Admin credential stays server-side. The server challenge store enforces six digits, 10-minute expiry, 60-second resend, **five total sends per normalized email per hour across all purposes**, and five failed attempts per challenge followed by a 15-minute cooldown without revealing account existence.

This design is conditional: prove that public native `/otp`, `/verify`, `/resend`, `/recover`, `/signup`, `/user` and pre-existing/refresh-token paths cannot provide an alternate password-update or weaker-recovery route. `MagicLinkEnabled=false` in reviewed GoTrue source may disable native Email OTP, but does **not** establish that native `/recover` or every existing token is closed; managed-hosted availability is unverified. A Custom Access Token Hook can be evaluated as a provider boundary, but its purpose signal, failure behavior and old-session handling require direct proof. If managed Supabase Auth cannot close or enforce those alternate paths, the controlled flow is **not feasible under the strict policy** on that configuration; return to the owner for an Auth hosting/provider decision. Never classify UI separation, RLS or client-side session clearing as that proof.

## Proposed server-owned challenge contract — not implemented

1. A trusted server generates six decimal digits with a cryptographic RNG. Store a keyed digest of `(purpose, normalized-email-key, challenge-id, code)` using a server-only pepper; never store or log plaintext code, password or full token. Keep minimal encrypted or HMAC-keyed email/purpose metadata and bounded retention. Do not put service-role or pepper in Expo.
2. Reserve send atomically against a shared normalized-email quota across signup and recovery: at most five total sends per email in a rolling hour and at least 60 seconds between sends, plus IP/device and project-wide defenses. Purpose-specific limits may be stricter but cannot reset the shared quota. Use a row lock or equivalent serializable transaction, an idempotency key, a monotonic generation and a transactional outbox so concurrent cross-purpose sends cannot exceed quota. Define behavior for provider failure before charging or releasing a reservation; do not let resend revive an earlier code.
3. Each challenge expires at `issued_at + 10 minutes`. Verification serializes on the challenge row, compares the digest in constant time, checks purpose/UUID/generation/expiry/consumed/lock state, and commits one attempt result. On the fifth wrong attempt set a server-owned `cooldown_until = now + 15 minutes`, reject even a correct concurrent attempt, and require a fresh challenge after cooldown (the old code remains expired/invalid). One successful attempt atomically consumes the challenge; retries return a generic non-session result. Lockout scope across resend and email/account must be defined and tested so an attacker cannot reset the budget with a new challenge.
4. Keep public responses uniform for existing, provisional, deleted and unknown accounts. Email and timing differences still require measurement; never expose a lookup endpoint. Recovery may send only for a password-complete account, but the public response stays generic. Completion must recheck the exact server-owned UUID and lifecycle under lock, exclude established/bound accounts from provisional cleanup, and reconcile Admin API success with lifecycle transaction failure without duplicate identity or double password update.
5. Protected cloud rows/functions/storage still check server eligibility and UUID ownership; a verified OTP alone grants neither Home nor protected resources. Offline and encrypted local binding remain separate gates. No automatic workout upload.

The challenge store, email outbox, lifecycle transitions and admin-key boundary require a separately approved migration/server slice. Six-digit codes have limited entropy; rate limits and monitoring are required. Built-in hosted mail currently cannot deliver public signup to arbitrary addresses under its [documented team-address and two/project/hour restrictions](https://supabase.com/docs/guides/auth/testing-auth-flows). External mail sender/domain approval is a separate gate; Brevo remains disabled.
