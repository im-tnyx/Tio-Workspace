**Status as of 2026-11-14:** Initial intentions derive from the product brief. **ADR-009–015 record owner-selected architecture, local tooling, single-account/MVP behavior, personal-backup UX, exclusive cloud-mode policy and future optional paid Sync business scope**. None approves cloud integration or billing implementation. **No deployment or Phase 1 implementation is approved yet**.

## Proposed ADR-019 — pending owner review (2026-11-15)

The owner has selected a **fixed signup UI sequence: Email → OTP → Password** (do not reorder), then **Account Setup (Username required + Mobile optional on the same screen)** → **Name (separate next screen)** → DOB (**required**) → Sex (**required**) → Units → Height → Current Weight → Activity Level → Goal → **one Final Setup screen (progress circle → Done checkmark → bottom Continue)** → Home. The screenshots are layout references only: **no stars, ratings, testimonials, or promotional cards**; Continue appears only after real completion. A **private minimal Supabase profile** is proposed for username, name, DOB, sex and optional mobile; workouts and fitness inputs remain device-local. **Additional proposed cloud account fields:** Avatar via **`profiles.avatar_url`** pointing to an owner-owned image in a **private Supabase Storage bucket** (optional Profile Settings upload or separately approved Google signup photo import; **new URL saved before old avatar object is deleted**, no extra required signup screen), **Plan** as server-owned tier `FREE` by default (not a workout plan and not a shipped paid feature), and **Platform / OS version / App build** as a private, latest-known, nullable account-client snapshot updated only on authenticated online use. These are proposals with extra data/privacy approvals, not deployed tables, buckets, billing or telemetry. The existing Auth-only cloud boundary would change **only after separate schema/privacy approval**.

**Additional owner-requested policy proposal:** cleanup abandoned Supabase signup accounts over time, with proposed **7 days for never-verified** and **30 days inactive for verified-but-never-activated** identities (7-day warning to verified email). **Never auto-delete protected/bound accounts or users who have merely left local fitness onboarding incomplete.** A server-owned activation marker, eligibility gates, safe admin deletion, cron job and exact duration approval are **pending**, not deployed. **New separate owner request for established FREE accounts:** consider eventual deletion after **6 months or 1 year of non-use**; recommended **6-month reminder, 11-month advance warning, and 12-month review-only expiry checkpoint**. Offline-only use and uninstall cannot be reliably distinguished from server silence. Deleting the Supabase UUID could strand encrypted local workouts; **no established-account auto-delete is approved** pending explicit owner risk acceptance and a tested identity/recovery/privacy plan. Do not confuse this with the 7/30-day abandoned-signup rules. See the [proposed ADR-019](25-MINIMAL-CLOUD-PROFILE-AND-LOCAL-ONBOARDING.md). It is **not** a deployed or accepted migration; existing ADR-017 presently calls username optional and describes Email + Password → OTP. Those legacy descriptions are flagged for reconciliation against the newer owner-selected flow and actual provider feasibility; do not change the fixed UI order. RLS, DOB/sex privacy, age policy, deletion, OTP anti-abuse and native encryption remain separate security/implementation gates. No real Auth/DB implementation authorization results from this proposal.

## Remaining product choices and settled MVP policies
1. **Tnyx name and Android/iOS ID `com.tnyx.tio`, minimal Neutral Black/White/Gray default, future optional user-selectable accent colors (not MVP), and English-only system fonts now, future Custom/Hindi separately (ADR-018) (ADR-016).** App ID verification/icon, exact neutral palette/Glass QA, future preset list, font license, native System preference and scroll motion remain pending.
2. **Decided for MVP:** Supabase email/password **with mandatory email OTP signup verification and anti-abuse limits (ADR-017)**; no guest/anonymous workout access. Previously verified same-bound local offline workouts remain permitted. Google/Apple login remains optional later.
3. **App PIN/biometrics deferred beyond core MVP (ADR-017)**; future recovery/lockout UX requires separate decision and must never replace true Auth/account isolation.
4. **Policy chosen:** logout locks and retains data/binding; confirmed device erase/reset is separate; server account-deletion UX/retention still needs future design.
5. **Policy chosen:** independent portable user-held recovery secret and **Local Only default**. After clear-data/reinstall, **Personal Backup** requires explicit matching encrypted archive Restore; future **previously enabled Supabase Sync** may auto-download available same-user server workouts instead; otherwise local history is empty. Exact recovery KDF/provider integration, future sync/transition/deletion behavior, automatic schedule and lost-key UX still require review.
6. iCloud integration route, feasibility and backup frequency under OS restrictions.
7. AI vendor, model, quotas, user consent copy and costs.
8. Scope of exercise catalog and any third-party licensing.
9. **Decided:** paid membership/paywall launches **only after core app MVP is complete** (ADR-017), with future full-workout Supabase Sync requiring separate owner opt-in **in addition** to paid entitlement. For now define extensible domain boundaries only, **no membership logic/UI/provider/deployment in Phase 1**. **Open:** price, billing provider, renewals, export/retention and deletion.
10. Minimal analytics policy and opt-in consent.

## Phase 0 decision-review package (recommendations pending)

The [Phase 0 Decision Review Pack](17-PHASE-0-DECISION-PACK.md) tracks **D02–D06 policy choices, D10 MVP catalog scope, D13 tooling and D14 shell/theme policy as owner-selected**, while D01, D07–D09, D11–D12 details and native/security verification still need follow-up, informed by the [offline session state machine](18-OFFLINE-SESSION-STATE-MACHINE.md), [encrypted backup recovery](19-BACKUP-RECOVERY-STRATEGY.md), [MVP UX flows](20-MVP-UX-FLOWS.md) and [Phase 1 readiness checklist](21-PHASE-1-READINESS.md). Remaining recommendations are not automatically approved; ADR-010/011/012/013/014 record selected tooling/policies, while unresolved details are tracked in [GitHub issue #2](https://github.com/im-tnyx/Tio-Workspace/issues/2).

Important: Offline access to already-verified local data cannot guarantee real-time enforcement of a remote session revocation while the device has no network. The owner accepted this trade-off for previously verified local access (2026-11-14); its timeout and optional local lock UX remain implementation questions. Local database encryption keys and portable backup recovery secrets must also be considered separately.

When a decision changes, update the relevant requirements/architecture/security/test documents first; log the change here with rationale and approval. Implementation starts only after Phase 0 review.
